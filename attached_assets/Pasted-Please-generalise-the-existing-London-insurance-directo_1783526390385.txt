3. IMPROVE CAREERS→BOARD RESOLUTION
====================================

Objective:
Reduce the number of employers whose “careersUrl” points at JS-heavy corporate pages that don’t yield jobs, by resolving through to their underlying ATS/board URLs.

Implementation:

1) Add a resolution layer, e.g.:

- src/lib/directory/resolveCareersBoard.ts

Behaviour:

- Given a `careersUrl` (from the directory) and optional HTML snapshot:
  - Detect if the page is primarily a shell that redirects/embeds an ATS board (Workday, Teamtailor, Recruitee, Workable, SmartRecruiters, Lever, etc.).
  - Follow redirects and discover the real ATS board URL where jobs actually live.
  - Store that resolved ATS board URL alongside the original careersUrl.
  - Update platformHint accordingly (e.g. “workday” instead of “generic”).

2) Use existing ATS detection & patterns:

- Leverage the ATS provider detection logic you already have (hostContains, pathContains, htmlHints).
- When a generic careers scrape finds a clear ATS pattern but no jobs because content is JS-heavy, treat that as a hint to capture the board URL and switch ingestion over to ATS mode.

3) Update ingestion:

- For employers where `resolvedBoardUrl` is known:
  - route through ATS fetchers using that URL/token.
- Only fall back to Firecrawl generic scraping when:
  - no ATS provider can be detected,
  - or a true custom/non-ATS careers page exists.

4) Diagnostics:

- Enhance the zero-job list to distinguish:
  - “careers page resolved to ATS board, but ATS fetch yielded 0 jobs”
  - “careers page unresolved / no board detected”
  - “careers page resolved but content is empty / no active postings”

Acceptance:
- Fewer employers sit in the “zero jobs due to JS-heavy corporate page” bucket.
- More of the directory employers produce jobs via ATS fetchers when boards exist.
- Diagnostics report improved and more granular reasons for zero jobs.
